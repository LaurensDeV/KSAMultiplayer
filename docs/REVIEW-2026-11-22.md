# Review of 2026-11-22: the evening on ksamp.gg, and what to fix from it

The busiest session the public server has had: up to eight players, a mid-session redeploy from
0.31.0 to 0.32.0, and one player's game crashing on entering the editor. Read afterwards from:

- the server log, 18:00–22:17 UTC. 20:49–21:14 is gone from `docker logs` with the old container but
  still in journald: `journalctl CONTAINER_NAME=ksamp-server`.
- the mod logs of Goddchen, Onyx, SafeShows (four launches) and SirAbgehoben, and Onyx's KSA log.
- the VPS's `dockerd` journal for the redeploy.
- the mod at 0.31.0 and 0.32.0, decompiled KSA 2026.11.16.5901, and the StarMap 0.5.4 actually
  installed (decompiled).

Each finding was investigated, then attacked by a separate pass whose job was to break it. What
survived is below, with its verdict. **Confirmed** means the code and the logs both show it.
**Likely** means every link is in the code but one piece of evidence from a player is still missing.

Line numbers are as of `652f275` (v0.32.0). `K/` is `../ksa-game-assemblies/current/src/KSA/KSA`.
Nothing here is fixed yet, and none of it is a `fix` until it has been seen in a game.

This is a plan, ordered by what it costs players times how often it happens. Tick the boxes as work
lands; each item says how to tell it worked.

## 1. Crashes and lost play: fix first

### 1.1 A launch can be named after a craft that already exists, and that can take the Sun out of KSA's world (Likely)

KSA names a new craft once, when the editor opens (`K/VehicleEditingSpace.cs:96`,
`GenerateNewVehicleId` checks `CurrentSystem.All`), and launches it under that name without looking
again (`K/VehicleEditor.cs:2674`). Its launch menu does look again (`K/VehicleLaunchMenu.cs:371`).
The mod's `AfterNewVehicleId` (`src/Mod/Hooks.cs:668`) also runs only when the editor opens.

In a shared world, other players' craft keep arriving while you sit in the editor
(`RefreshVehiclesInFrame` runs there, and so does `Settle`). If one of them takes the name your
editor picked, your launch registers a duplicate:

1. `LookupCollection.Register` (`K/LookupCollection.cs:110-135`) logs `error registering duplicate`
   and returns. The craft is never added to `_all`, its `LookupIndex` stays 0, but the editor still
   adds it to its body's `Children` (`K/VehicleEditor.cs:2675`). It is never simulated: a rocket that
   will not leave the pad. `World.Vehicles()` cannot see it, and `TakeRenames` says "yours no longer
   exists" when the server's rename comes back (`src/Mod/Sync.cs:2117`).
2. Recovering or deleting it disposes it, and `Deregister` (`K/LookupCollection.cs:144-157`) removes
   by hash, which takes out the *other* craft's dictionary entry, then overwrites slot 0 of `_all`
   with the last entry. Slot 0 is Sol for the whole session (`CreateTreeFromRoot`,
   `K/CelestialSystem.cs:206`).
3. With Sol gone from `_all`, the Universe Manifest's tree, which walks `OfType<IIndependentRoot>`
   (`K/UniverseManifest.cs:264`), draws nothing, and `GetWorldSun()` (`K/CelestialSystem.cs:634`)
   returns null. A new-vessel editor dereferences it at `K/VehicleEditor.cs:1495`. Nothing catches
   that (`K/App.cs:39-72`, `K/Program.cs:1925`).
4. Worse, the other craft is now in `_all` but no longer in the dictionary. A later `clear` or
   destroy of it disposes a vehicle that stays in `_all`, which very likely throws in the same frame.
   That fits Goddchen leaving 0.44 s after Onyx's `clear` at 21:08:58.

Seen: the server renamed a clash three times (Goddchen 20:36:24, SirAbgehoben 20:37:49 and
21:47:17). Goddchen relaunched 22 s later, then reported an empty manifest and a crash on entering
the editor; his game left at 20:39:29 and again at 21:08:59.

A crash still sends a clean `Bye`: StarMap's `async Main` catches whatever leaves KSA and disposes
the mod loader in a `finally`, which runs `[StarMapUnload]` (`StarMap/Program.cs:7-27`,
`StarMap.Core/ModRepository/ModsLoader.cs:176-181`). So **"has left" does not tell a quit from a
crash**; only a native or worker-thread death shows as "has gone quiet".

Fix:
- [ ] In `BeforeEditorDispose` (`src/Mod/Hooks.cs:603`), when launching and `EditingSpace.Id` is
  taken locally (`World.Taken`) or, while playing, by another player (`Sync.SomebodyOwns`), set it
  to the first free `NewRocket_N` (the loop in `AfterNewVehicleId`) or `World.FreeLocalId`, and log
  it. This also covers a player typing a taken name.
- [ ] Defence in depth: in `World.Destroy` (`src/Mod/World.cs:899`), skip and log any vehicle for
  which `system.All.Get(v.Hash)` is not that same object.
- [ ] After `Settle`, check once that `GetWorldSun()` is not null, and log loudly once if it is, so
  the next occurrence explains itself.
- [ ] Correct the comment at `src/Mod/Hooks.cs:658-666`, and update `docs/DESIGN.md`.
- [ ] Report the missing launch-time name check to the KSA developers.

Verify: the in-game reproduction in section 0 no longer leaves a stuck rocket, and the manifest
survives recovering it.

### 1.2 A redeploy kills the server with no warning, no goodbye and no last save (Confirmed)

`dockerd` at 21:14:19: *"Container failed to exit within 0s of signal 15 - using the force"*, for
all three containers. The provider stops a container it replaces with no grace;
`infra/server/server.tf:83` sets `stop_timeout = 20`, which only `docker stop` uses. Players got
"lost connection: nothing from the server for ten seconds", not the goodbye. 21:12:08 to 21:14:19
(about 130 s of universe time) was lost, including two players' flights.

Even given time, the order is wrong. `Program.cs:762-765` says "shutting down", then
`announcer.Dispose()` withdraws from the directories for up to 4 s (`Announcer.cs:31,202`), and only
then `server.Dispose()` sends the `Bye` (`Server.cs:3008-3012`). Nothing asks for a last save.

Fix:
- [x] `destroy_grace_seconds = 40` (and `stop_timeout = 40`) on `docker_container.server` and
  `other_world` in `infra/server/server.tf`.
- [x] On SIGTERM:
  1. `Announce` "the server is restarting for an update, back in about 30 s".
  2. `AskSnapshot` and keep ticking until the world arrives (at most ~5 s).
  3. Send the `Bye`.
  4. Withdraw from the directories last.
- [x] A countdown (`stop-notice`, 15 s, drawn on screen in red by a `Closing` datagram, and said in chat) before stopping; joins refused meanwhile; a second stop ends it at once. The
  grace in `server.tf` must exceed it.

Verify: a redeploy shows "the server closed the connection: …" in a client log, and the restarted
server's universe time matches the last moment of play.

### 1.3 A joined client is never told that the server it lost now needs a newer mod (Confirmed)

A new hello from 0.31 to 0.32 is handled well: the bare `Alive` (`Server.cs:888-896`) carries the
version in its header (`Wire.cs:1016`), and the client says "install the newest"
(`Client.cs:529`); the browser says it too. A client that was **joined** ignores a foreign version
(`&& !Joined`, deliberate: a forged datagram must not kick anyone). It ends with "nothing from the
server for ten seconds" and is never told why. There is no automatic reconnect.

Fix:
- [x] Remember the last foreign version seen while joined, and append it to the timeout message
  (`Client.cs:582`): "… the server now speaks protocol 32: update KSA Multiplayer". A forged datagram
  cannot use that to kick anybody.
- [ ] Add the update link to "install the newest" (`Browser.cs:246-248`, `Client.cs:529`).
- [ ] Log refused wrong-version hellos on the server, rate-limited per address (`Server.cs:888-897`),
  so the operator can see who is locked out.

### 1.4 `fresh` at the console needs a guard (Confirmed)

At 21:16:25 and 21:16:46, after `docker attach ksamp-server` and `docker ps` had been typed into the
attached console, `fresh` was typed twice. The second one backed up the empty world that a restart
in between had loaded (`_worldKept` is reset by any load, `Server.cs:778`). Onyx loaded that empty
backup first, then the real one. Nothing was lost. But kept `before …` saves are trimmed to five
(`SaveShelf.cs:34`), and the real world was two more mistakes from the bin.

Fix:
- [ ] `fresh` asks for confirmation (`fresh <system> confirm`, or the same command twice within
  30 s; `Program.cs:650`).
- [ ] `fresh` refuses when the current world is already an empty stock world nobody has saved
  since, so it never backs up an empty world over a real one (`Server.cs:2842`).
- [ ] The "kept as 'before fresh …'" line and the in-game saves list show each save's size and
  universe time (the console `saves` already does, `Program.cs:567-570`).
- [ ] Print "detach with Ctrl+P Ctrl+Q; Ctrl+C stops the server" when a console attaches, or
  provide `docker exec ksamp-server ksamp-ctl <command>` and drop `tty`.
- [ ] Correct `Program.cs:647-649`: it calls `fresh` console-only, but `Permissions.cs:47` lets an
  admin run it.

## 3. Watching another player's craft

### 3.1 The top-left gauges show the craft you last flew, not the one you are watching (Confirmed)

Reported in the session. The speed digits come from `Program.VelocityRoller`
(`K/GaugeDigitBinding.cs:42`), filled only by `UpdateGauges(ControlledVehicle, …)`
(`K/Program.cs:2554-2556`, `:3042`). Clicking another player's craft moves the camera
(`Camera.SetFollow`, `K/Camera.cs:608-622`), and then `BeforeControl` refuses control of it
(`src/Mod/Hooks.cs:1160-1170`). So `ControlledVehicle` stays the craft this game controlled last,
and its speed, altitude, navball (`K/Program.cs:3253`), orbit hover readout (`K/OrbitHoverReadout.cs:39`)
and mission time keep showing it, live.

### 3.2 …and the keys still fly that craft, off screen (Likely; test in game)

`Program.OnKey` hands keys to `ControlledVehicle.OnKey` whenever `IsControlledVehicleActive`
(`K/Program.cs:2242-2246`). A player watching someone else may be throttling or staging their own
craft without seeing it.

Fix for both:
- [ ] Minimum: when `BeforeControl` refuses, also let go of control (`Program.ControlledVehicle = null`
  through the setter, which is not refused for null, or `World.LetGo`). The gauges then disappear
  rather than lie, and keys reach nothing. `MapController.PreviouslyControlledVehicle` and the
  existing fly path take the own craft back.
- [ ] Better, on top of that: show the watched craft. Either wrap the gauge section of
  `Program.OnFrame` (or `UpdateGauges` plus `UpdateShaderData`) with a prefix/finalizer that sets
  `Program._controlledVehicle` (field ref, bypassing the setter hook) to the followed craft and
  restores it, after checking puppets' `NavBallData` is fresh (`K/Vehicle.cs:2949`). Or draw the
  mod's own speed and altitude line in the panel.

### 3.3 Looking at craft takes them over (Confirmed)

The server frees a craft whose owner has not been near it for 10 s to whoever's camera is on it
(`Lapse`, `Server.cs:2266-2273`, owner set to 0). Cycling the camera through craft therefore frees
them one after another:
- SafeShows flicked through about 60 craft in a minute (21:35:29–21:36:36). About 30 were freed for
  him, and his game took several, including Purrpose One at 182 KB.
- Those craft were then handed around for 20 minutes (21:47–21:53, "SafeShows has not been near
  it").
- Goddchen did the same at 20:38, 21:41 and 22:03.

Across all 330 frees: 61 went to the player they were freed for, 22 bounced back to the previous
owner, 27 went to someone else, and 220 changed nothing. The watcher is often flying something else,
and only a game flying nothing takes a watched craft (`Sync.cs:528-532`), while the client reports
the camera's target as watched regardless (`Sync.cs:1600`).

Fix:
- [ ] In `Lapse`, free only for a watcher who is flying nothing (`q.Controlling.Length == 0`),
  which is what DESIGN.md:385-389 already says.
- [ ] And only for a watcher who has watched that craft for a few seconds, so flicking through the
  vessel list takes nothing.
- [ ] Keep a freed craft for the named player briefly, so a nearby game's near-claim
  (`Sync.cs:2574-2583`) does not snatch it.
- [ ] Log in the mod why each claim was made (flown, near, watched) and when one is refused or lost.

## 5. Craft sync: bandwidth and rebuilds

### 5.1 Taking a craft over re-sends all of it, to everyone, and every game rebuilds it (Confirmed)

Of 5.4 MB of craft descriptions sent this session, only 0.5 MB were each craft's first. Purrpose One
was about two-thirds of the rest: 160–240 KB, sent 21+ times. Every send follows a takeover (3.3).
A taken craft starts with `Shape = 0` (`Sync.cs:2405`), so it is always described again. The server
relays every description to every loaded game (`Server.cs:1491`), and each game tears its copy down
and builds it again: about 140 ms per game for Purrpose One, 8–13 times per game per session.

- [ ] Fewer takeovers (3.3) is most of the fix.
- [ ] Skip the re-describe on takeover when the server already holds this game's last definition
  of the craft and nothing has run on it since.
- [ ] **Do not** skip near-identical rebuilds by size. Fuel and part state travel in the
  definition, which is how a station's fuel reached the other game (DESIGN.md:600-610).

### 5.2 New debris is always described twice, 2 s apart (Confirmed)

`Own(define: true)` sends the first description at once (`Sync.cs:2208`). In the same `Play`,
`SendOwned` finds the server has not named this game the owner yet (`OwnerOf` is 0 until the roster
comes back) and lets the craft go (`Sync.cs:2455-2462`). When the roster arrives it is taken again
with `Shape = 0` (`:2405`), and redescribed as soon as `MaySayHow` allows, 2 s later.

- [ ] Do not let go of a `Mine` claimed moments ago and not yet granted. Give `Mine` a `ClaimedAt`,
  and require it to be more than ~5 s old before letting go on `owner == 0`. Or, at `:2405`, keep
  the real shape when this game has already described it. Other games still get the debris as fast
  as now.

### 5.3 Changing which body a craft goes round re-sends all of it (Confirmed in code, not seen this session)

`World.Shape` hashes the body (`World.cs:322-323`), and a change of shape is a full describe
(`Sync.cs:2467-2475`). Commit 1099270 added it so a late joiner did not build a Moon craft at the
Earth. Since then every new copy is re-placed from its owner's newest state, body included
(`Sync.cs:3136`), and a copy found round the wrong body is moved (`Sync.cs:3091-3096`).

- [ ] Drop the body from `Shape`, after checking nothing reads `ParentBody` from a stored
  definition (saves included).

### 5.4 A name-clash rename leaves the server holding a craft that does not exist (Confirmed)

When the clashing craft never existed (1.1), the client says "yours no longer exists" and moves on
(`Sync.cs:2117-2121`). The server's record under the new name stays, and counts against
`RoomFor`.

- [ ] The client says `Gone` for the new name.
- [ ] Reword the message. As players see it, "another player already has a craft called
  'NewRocket_2', but yours no longer exists" says nothing they can act on.

### 5.5 A new craft whose name matches one nobody owns takes that craft over (Confirmed in code only)

`Server.cs:1559-1566` renames only when the name has a living owner. Otherwise the new definition
replaces the old craft in every world. KSA numbers split pieces per game, so `_N` names clash
between games regularly.

- [ ] Decide whether to rename here too. Mind the undocking case, a craft made again under its
  own name (`Server.cs:1526`).

## 6. Other players' craft out of place

### 6.1 A correction every 3.0 s that moves nothing (Confirmed)

36–48% of "was N m off its owner's orbit, and is put on it" lines say 0.0 m. They come in chains
exactly 3.0 s apart (`CoastingEverySeconds`, `Sync.cs:50`, `:2716`), in every game at once:
Keystone_1_2 was put on its orbit 202, 239 and 223 times in three games between 21:25 and 21:35,
while SafeShows was near it. The owner's `Rails` flag flickers (`World.cs:962`). KSA swaps a coasting
craft that shares the owner's bubble between Freefall and Maneuvering (`K/PhysicsBubble.cs:1447`,
`:1693-1722`). Every non-`Rails` word re-arms the put-on (`Sync.cs:2721`), which then fires at any
distance (`:2714`). Each one is `Vehicle.Teleport` (`World.cs:1336`, `K/Vehicle.cs:2516-2565`): out of
the bubble, a full trajectory, off rails. That is probably a twitch, and maybe broken contact with a
craft beside it.

- [ ] Never put on at under ~0.05 m (`:2714`).
- [ ] Re-arm only after a non-`Rails` word that had the engine on or lasted ≥0.5 s (`:2721`).

### 6.2 Under the owner's thrust a copy drifts kilometres (Confirmed mechanism, cause of the hold Likely)

The orbit put-on is off while the owner's word is not `Rails` (`Sync.cs:2687`), so during a burn
only `Pull` moves a copy. Above the near-surface radius KSA puts the copy back on rails every step,
which discards what `Pull` writes. And `Pull` holds when the owner's word is over 1 s old
(`World.cs:1137`, `:1175`). The copy coasts on the arc it was built on, with no thrust.
Abgehoben-sbm-004-Test was 122.5 km off in Goddchen's game and 124.7 km in Onyx's at 21:38:40; that
is ½·35 m/s²·83² ≈ 120 km. Space Tug was 14 km off. Then a ~1 m loop followed: Vector I_6 was put on
123 times in 83 s.

- [ ] While the owner burns and the copy is on rails here, put it on every 0.5 s when it is over
  ~25 m out (enter the branch at `:2687` when `World.UnderWay(v)` is false here).
- [ ] Measure the offset against the same orbit `Rebase` uses, and re-act only above ~1.5 m.
- [ ] Log, once a second per copy, whether `Pull` returned null or held and whether the copy was on
  rails. That settles the remaining doubt.

### 6.3 A game behind the clock corrects no coasting copy (Confirmed)

The coasting check and `Pull` both require the newest state's time to equal this world's
(`Sync.cs:2702`, `World.cs:1137`), which `Track.At` gives only within 4 s behind (`Clock.cs:256`).
After the 438x warp, SafeShows' game put on nothing for 33 s, then found Truss Launcher 4542 km off
(19:22:02).

- [ ] For coasting craft, carry the owner's orbit to this world's time instead of requiring
  equality. Factor `World.OrbitAt(said, universe)` out of `Rebase` (`World.cs:1329-1331`), and bound
  it (e.g. |Δt| < 600 s).

### 6.4 Copies break apart in their first physics step, and come back 5 s later (Confirmed; cause Likely)

There were nine cases, each 12–49 ms after the copy was built and always within a frame of its hull
being rebuilt. The pieces had the same names in every game (`PartFailure.ShedDebris` seeds
`Random(source.Hash)`), which points at `DestroyVehicleFromEvent` or `PartFailureEvent.Apply`. Both
are spared only for craft in `Puppets` (`Hooks.cs:242-245`, `:968`), and a fresh copy is not in
`Puppets` until `PlaceOthers` (`Sync.cs:2665`). The likely trigger is contact with the old hull copy,
or a load spike from the `Rebase` right after the build.

- [ ] Register the copy as a puppet where it is built (`Sync.cs:3121`), so it is spared from its
  first step.
- [ ] `WaitsForItsHull` (`Sync.cs:2746`) also holds a piece while its hull is in `Rebuilding`,
  `ToRemove` or `Deferred`.
- [ ] Log in `BeforeDestroy` and `BeforePartFailure` when the craft is in `Built` but not `Puppets`,
  with cause, G-load and contact.

Players saw this as "the station exploded on my end" and "umbrella things went flying after a weird
flash" (18:27–18:28).

## 7. Admin actions

## Refuted, so nobody looks again

- **The mod's 10-fault switch-off.** There was no WARN or ERROR in any mod log; it played no
  part. It is not silent either: the player is told.
- **The universe manifest padlock** (`ManifestLocks`, the transpiler in `Hooks.cs`). The IL and
  ImGui use are sound, and an exception there would crash rather than hide the window.
- **The mod renaming the duplicate craft.** A server rename only records `Renamed[]`; `World.Rename`
  runs for `Named` notices alone. What sets off 1.1 is a recover, delete or destroy.
- **A `clear` destroying the duplicate itself.** It is not in `_all`, so `World.Vehicles()` never
  yields it. A clear can only reach its half-registered twin (1.1, step 4).
- **Losing Sol crashing a game at once.** `Universe.WorldSun` is cached and the lighting null-guards.
  Only the editor calls `GetWorldSun()`.
- **A departing player's speed limit leaving with them.** That is correct: the departed machine
  cannot be left behind. The 438x came from the unvoted steer (2.2).
- **Skipping near-identical rebuilds.** Unsafe; see 5.1.
- **Craft count swings (−23, +18).** That is the server tidying craft nobody owns after a leave and a
  save (`Server.cs:2916-2927`). The −6 next to the 438x was a leave, not the warp.
- **Docking.** Every refusal was right. The owner's game missed each docking on roll or distance, and
  no docking showed in one game but not another. Only the wording "both are other players'" is
  misleading when one craft has no owner.
- **Onyx's four KSA errors.** KSA's update check, and next-vessel pressed in the empty world that
  `fresh` made.
- **The directory hostnames.** `servers.ksarmory.com` and `servers.ksamp.gg` serve the same list.
